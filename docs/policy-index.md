## Checklist de verificação

- [x] Texto gerado mantém a hierarquia dot para tarefas pequenas/preparação e HolyCodex Root para execução grande, preferência Root Sol/medium, especialistas Luna/high, Standard e Fast opt-in: `tests/cli.test.ts`.
- [x] Texto gerado mantém limites de máquina/browser, autonomia nos projetos autorizados, reutilização de aprovação informada para UAC/sudo/pkexec quando ação/dispositivo/escopo coincidem, sem senha no chat ou bloqueio geral do cloud, revisão baseada em evidências, visualização, dependências maduras, reuso de sessão e escrita de instruções autocontida: `tests/cli.test.ts`.
- [x] Pedidos iniciais de decisão/ação/aprovação usam ferramenta estruturada ou controle dedicado e nunca opções em texto comum: `tests/cli.test.ts`, `tests/setup.test.ts`.
- [x] Setup gera proposta limitada, não concede regras, reutiliza aprovação informada quando aplicável, não pede senha no chat e não cria proibição geral do cloud: `tests/setup.test.ts`.
- [x] Intervalo local de status valida configuração; instruções suprimem mudanças substanciais imediatas, permitem apenas pronto para merge pedido explicitamente e enviam lembretes separados somente para pedidos essenciais ainda sem resposta/ciência: `tests/cli.test.ts`, `tests/setup.test.ts` e `tests/validate.test.ts`.
- [x] Primeiro setup cria configuração local atômica sem sobrescrever; repetições, prévias e entradas inválidas não alteram configuração existente: `tests/cli.test.ts`.
- [x] Integridade do pacote, links, licença, workflows e releases continuam cobertos: `tests/validate.test.ts` e `tests/release.test.ts`.
- [x] Campos de handoff cobrem objetivo, escopo, abordagem, fontes, decisões, dependências/acessos, riscos e testes/autorização: `tests/validate.test.ts`.
- [x] Cenários de uso, handoff Root, reuso de sessões e limites estão descritos para avaliação manual: [aceitação](../examples/acceptance.md).
- [x] Hipótese de custo ponderado API-equivalente fica em documentação de manutenção e não é injetada nas instruções executoras: teste de documentação em `tests/validate.test.ts`.
- [ ] Comportamento do modelo ou disponibilidade de HolyCodex Root, formulários, browser, computador, controles de modelo, conexões e CI do host não podem ser provados pelos testes locais; veja as limitações abaixo.

## O que não foi implementado

O preset embedding futuro do HolyCodex, os presets de instalação em Codex Cloud e os serviços de sincronização de conta são propostas, não recursos deste pacote. Não há endpoint de importação automática de um dot, acesso criado por leitura de arquivo ou aceitação automática de regras em nome do usuário.

Política de eficiência: reuso de sessões, contexto estável, recuperação focada e handoffs concisos são práticas de fluxo. Avaliações externas devem considerar tanto entradas em cache quanto novas e o total combinado, sem inflar o cache com contexto irrelevante. O pacote não afirma economia ou proporções específicas sem benchmark representativo.

O pacote não controla se o host oferece um HolyCodex Root, formulários de aprovação dedicados, ferramenta estruturada de perguntas, seletores de modelo/velocidade, navegador, computador, conexões ou verificações de CI. Esses recursos precisam ser verificados no ambiente real. Os testes automatizados verificam texto, configuração local, integridade do pacote e release; os exemplos de aceitação são avaliação manual e não certificam o comportamento do host.

Permissões temporárias de uma tarefa, como uma elevação local específica, não são padrões globais. O pacote não contém detalhes de computadores, projetos privados ou regras salvas de uma pessoa.
